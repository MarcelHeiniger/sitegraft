# Definition of Done — sitegraft

> The objective criteria that say "this is done." An external dev should be able to
> check this list and know, unambiguously, whether their work is acceptable.

## Project DoD (v1 — a tool usable for a real run)

The v1 project is considered delivered when:
- [ ] All 6 phases (`scan`, `plan`, `backup`, `graft`, `verify`, `restore`) are
      implemented and individually runnable via the CLI
      (`sitegraft <phase> --profile <name>`).
- [x] The 2 shipped v1 modules (`core-wp`, `etch`) work end-to-end on the
      DDEV harness (`core-wp` via real auto-detection; `etch` via the
      harness's own hand-written manifest, since its site A fixture
      simulates Etch content through a mu-plugin, not a real "etch" plugin
      entry `etch_detect` can see — see `modules/etch.sh`'s header comment).
      **`acss` is deliberately NOT shipped in v1** (corrected 2026-08-20,
      Step 6 self-review): `modules/acss.sh` was speced in the design doc
      (§3.4) but never created, because that spec's own
      `TODO_VERIFY_LEGACY_ACSS_SLUG` blocker — the pre-4.0 Automatic.css
      plugin folder name — has never been checked against a real install.
      Shipping it with a guessed slug would violate the design doc's own
      explicit instruction not to. See `docs/todo.md` → Backlog.
- [ ] A full `scan → plan → backup → graft → verify` run succeeds on the DDEV
      harness without altering a single byte of B's fake protected plugin data
      (an automated byte-identical assertion, not a visual check).
- [ ] The `restore.sh` generated by the `backup` phase restores B to the exact
      pre-`graft` state — **for an ssh-remote or genuinely local (unwrapped)
      B**, tested on the DDEV harness's bare-local branch (deletion of a file
      added since the backup is verified, not merely overwrite of an existing
      one). Scope amended in the Step 3 fix-pack review (Viktor/Kimi): a
      **wrapped-local B (e.g. DDEV itself, used only as this harness's own
      test double)** is documented and tested as **overwrite-only** —
      Mutagen-style container syncs can make the underlying directory
      un-removable ("Device or resource busy"), so that path never attempts
      to delete files added since the backup, only to overwrite files the
      backup contains. This does not weaken v1's real target (an operator
      restoring a genuine ssh-remote or bare-local B, per design doc §5.1's
      profile shapes) — it only means the DDEV harness itself, being a
      wrapped-local site, cannot be used as evidence of exact-state restore
      on its own default branch, and the harness now exercises the
      deletion-guaranteed branch directly (bare-local, against B's real
      host-filesystem wp-content) specifically to keep this item honestly
      checkable rather than green-by-a-test-that-cannot-fail.
- [ ] `--dry-run` works on every phase that writes (`backup`, `graft`, the
      optional `clean` sub-step, `restore`).
- [ ] Adding a new module (e.g. the hypothetical `motopress.sh` documented as an
      example in the design doc) requires no change to any file in `lib/` or
      `bin/` — only adding a file under `modules/`.
- [ ] `graft` refuses to run on a rendering-stack mismatch (active theme / Etch /
      ACSS version) between A and B unless launched with `--allow-stack-mismatch`,
      which itself requires an explicit, loud confirmation (design doc §12).
- [ ] Unit tests (`bats`) are green for every pure function in `lib/`.
- [ ] DDEV integration tests are green: protected data isn't contaminated, AND the
      positive assertions hold (migrated options carry A's exact values,
      `page_on_front` resolves to the correctly remapped page, A's domain string is
      absent from B's imported content — design doc §10, not merely "some content
      exists on B").
- [ ] `docs/usage.md` (or a README section) lets someone unfamiliar with the tool
      run a first pass without any other help.
- [ ] The repo is ready to publish on GitHub: MIT LICENSE present, a
      public-facing English root README, zero secrets/real hosts/IPs/client names
      anywhere in the git history (not just HEAD).

## Pre-`1.0.0` gate (blocks the version tag specifically, not v1 feature-completeness)

- [ ] **A first real dry run on a staging copy of a genuine A/B pair** — not the
      DDEV harness's simulated fixtures. This is the only thing that closes design
      doc §0.2's R2 (the two-pass sentinel ID remap has only been validated by
      reasoning against simulated Etch content, never a real export from a real
      Etch license) and R4 (no pilot run means the DDEV harness proves the
      mechanics, not the real-world variety of Etch content and third-party
      plugins actually encountered). Every other DoD item above can be checked by
      DDEV-only testing; this one deliberately can't — don't substitute another
      DDEV run for it. Until this is done, ship pre-releases as `1.0.0-rc*`, not
      `1.0.0` (see `docs/plans/2026-08-19-sitegraft-implementation.md`, Task 6.3).

## DoD per task / PR (reminder)

Every contribution must:
- [ ] Pass the relevant `bats` unit tests (see `infrastructure.md` → CI)
- [ ] Be tested under real conditions (DDEV for anything touching `graft`/`backup`),
      not just reviewed as code
- [ ] Not regress existing behavior (rerun the full DDEV harness before merging any
      task touching `lib/`, `modules/`, or a phase)
- [ ] Never introduce raw SQL filtered by hand for content — only WXR
      (`wp export`/`wp import`) for content, `wp option get/update` for options,
      targeted `wp db export --tables=` for plugin-owned tables
- [ ] Never use `sed`/raw regex on serialized WordPress data — always
      `wp search-replace` (safe on serialized PHP data)
- [ ] Document any change to the module contract in the design doc
- [ ] Bump the version in `bin/sitegraft` (see `../CLAUDE.md` → Conventions) if the
      change affects user-visible behavior

## Specific acceptance criteria

- **Non-contamination:** any data belonging to a post_type, option, or table
  declared by a protection module on B (i.e. present on B but absent from the
  migration selection) must be bit-for-bit identical before and after `graft` —
  verified by checksum, not visual inspection.
- **Safe default (default-deny):** any post_type/table/option detected on B but
  not covered by a known module must be listed as "protected by default" and
  never touched without an explicit selection in the manifest.
- **Idempotence:** rerunning `graft` with the same manifest against a B that's
  already been grafted must neither duplicate content nor corrupt state (see
  design doc → idempotent reimport edge case).
- **Portability:** the tool runs unmodified on macOS (stock bash 3.2) and on
  Linux/WSL (bash ≥ 4), with no dependency on a specific machine or host.
